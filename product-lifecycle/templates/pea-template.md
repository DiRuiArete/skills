# PEA 模板（产品体验评估）

> Product Experience Assessment — 理想汽车所有产品动作的起点。任何功能/方案在策划阶段必须填完六个维度，通过评审才能进开发。**僵化执行，没有例外**。

## 使用提示

- 凡是涉及产品决策（功能、方案、营销动作、UI 调整）都要走 PEA，**不分大小**
- 没填清楚的维度 = 评审被打回
- 评审通过后六维度变成复盘的对照基准（→ 见 retro-template.md）

## 模板

```

发起人：[XX]
日期：[YYYY-MM-DD]

（必须拿出具体依据，证明这是真问题；
 证明不了真问题 → 评审打回）

来自的用户群：
（不是"所有用户"——必须是清晰可识别的人群）

（用户反馈 / NPS 数据 / 调研观察 / ……）

──────── 二、目标要素 ────────

用户场景：

（可衡量、有时间限制）

  与目标的关系：[XX]
  事先预期值：[XX]
```

## 填表注意事项

### 一、解决什么问题——最容易翻车的维度

不能写"我觉得这个功能好"——必须证明**真问题**。

判断真问题的标准：
- 有用户反馈说现状不好（NPS、客服记录、共创会发言）
- 有数据显示痛点存在（使用频率低、留存差、转化差）
- 没数据支撑 → 一律打回

### 二、目标要素——警惕"我们自己的描述"

错例："我们要让用户体验更好"——这是 PM 自己的话。

正例："用户在做 X 时，能在 Y 秒内完成 Z，并且觉得'比上次顺多了'"——可以**从用户嘴里说出来**。

### 三、产品方案——避免"功能列表"

不只是列功能——要写**实现方案 + 体验细节**。

体验细节维度：
- 看见的：UI、视觉、文字
- 听到的：声音、提示
- 触摸的：物理交互
- 感受的：情绪、惊喜点

### 四、风险预案——这是最常被跳过的

"应该没什么风险"——这种回答 = 评审打回。

至少列 3 个风险 + 每个的预案。

### 五、资源评估——不要乐观估算

PM 通病：低估研发周期 / 高估自己团队效率。
建议：所有资源估算**乘以 1.3-1.5**。

### 六、运营指标——数据化是硬约束

不能写"用户满意度提升"——必须可量化。

例：
- "试驾预约转化率从 20% → 30%"
- "用户主动分享率从 5% → 10%"
- "NPS 提升 5 分"

## 评审流程

```
1. 发起人填写 PEA
        ↓
2. 提交评审会
        ↓
3. 评审委员（产品 + 研发 + 业务）逐条审
        ↓
4. 通过 / 打回 + 具体打回理由
        ↓
5. 打回 → 修改 → 重新评审（标记第 N 次）
        ↓
6. 最终通过 → 进开发
        ↓
7. 上线后回填实际效果（→ 进入复盘）
```

---

## 与复盘的对接

PEA 评审通过后，六维度变成复盘的**对照基准**：

```
PEA 第六维度（运营指标预期）  →  复盘时的"对照计划"
PEA 第四维度（风险）          →  复盘时的"哪些风险真的发生了"
```

→ 详细见 `retro-template.md`
